# 内网部署手册 —— 两种场景

适用前提：**你在本机的 PostgreSQL 是准确的、与当前程序版本匹配**，因此本机结构即"目标结构"。

`backend/deploy/` 的职责边界（先记住这条，两个场景的命令差异全由它决定）：

- 它只做两件事：**建库/建用户/授权** + **版本化迁移（补列/补表/记版本）**。
- 所有迁移语句都是 `IF NOT EXISTS`，**只增不删、可重复执行**。
- **ORM 基础表不由它建**，而是由各模块 `init_database()`（内部 `create_all`）建立。

由此推出两个场景的分工：

| 库的状态 | 缺什么 | 对应命令 |
|---|---|---|
| **库已存在**（内网A） | 只缺历史增量列/表 | `--migrate-only` |
| **库不存在**（内网B，空库） | 缺库、缺用户、缺**全部基础表** | `--bootstrap` |

> 一句话记法：**已有库 = 补迁移；空库 = 先建基础表再补迁移。**

---

## 公共前提（两边都要做）

1. 复制到内网的是**当前这套准确版本的程序**，且**包含 `backend/deploy/` 目录**。
2. 内网机能跑后端同款 Python 环境，且已装 `psycopg2`、`python-dotenv`
   （离线环境可用开发机的同版本 wheel 离线安装）。
3. `backend/.env` 指向**该内网自己的** PostgreSQL：
   ```
   POSTGRES_HOST=localhost
   POSTGRES_PORT=5432
   POSTGRES_ADMIN_USER=postgres
   POSTGRES_ADMIN_PASSWORD=******   # 改成该内网的真实管理员密码
   ```
   > 注意：`code_review` 与 `code_review_regression` 用的是各自的 `POSTGRES_DB` / `POSTGRES_DB_REGRESSION`；
   > 其余模块是 `AUTH_/STATIC_/FPGA_/OPTO_/MAINTENANCE_` 前缀变量（默认值见 `deploy/db_config.py`）。
   > 若各模块密码不一致，把变量写进 `.env` 即可，无需改代码。
4. 命令都在 **`backend/` 目录下**执行。

## 场景一：内网A —— 已有数据库，字段与开发机"基本接近"

**核心动作：先对账，再增量补。** "基本接近"意味着可能有隐藏差异，不能盲跑。

### 步骤

**1) 先备份（必须，不可跳过）**

在 内网A 上对 7 个库逐个全量备份：

```bash
for db in auth code_review code_review_regression static_analysis_filter fpga_static_analysis_filter opto_knowledge maintenance; do
  pg_dump -h localhost -U postgres -d "$db" -f "${db}_$(date +%Y%m%d).sql"
done
```

> Windows 可写成 `.bat`（逐条 `pg_dump ...`），或用 Navicat 的数据传输/备份功能。

**2) 放入新版程序，配好 `.env`**（见公共前提）。

**3) 只读体检 —— 看还差几个迁移**

```bash
python deploy/deploy_db.py --verify
```

- 显示 `pending` → 缺的迁移一目了然。
- 显示"无法连接/库不存在" → 检查 `.env`、库名、管理员密码。

**4) 结构对账（推荐）—— 专治"基本差不多"里的隐藏差异**

迁移只能补"它知道的缺列"，补不了"类型不同 / 多了列"这类漂移。做一次清单比对最稳。

在**开发机（准确）**和**内网A**上各执行一次，导出后对比：

```sql
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
ORDER BY table_name, column_name;
```

导出成 CSV 再 diff，例如：

```bash
psql -h localhost -U postgres -d code_review -A -F, \
  -c "SELECT table_name,column_name,data_type FROM information_schema.columns WHERE table_schema='public' ORDER BY 1,2;" \
  > code_review_columns.csv
```

> 也可以用现成工具：两边各跑 `python deploy/snapshot_schema.py`，然后 diff 两份快照文件。

**判定：**
- 差异**只是"内网A缺列"** → 交给迁移，放心跑。
- 出现**"类型不同"或"内网A多列"** → 属于迁移覆盖不到的漂移，**先人工确认再动手**，不要硬跑。

**5) 演练（不落库）**

```bash
python deploy/deploy_db.py --dry-run
```

**6) 正式迁移（库已存在，不建库）**

```bash
python deploy/deploy_db.py --migrate-only --yes
```

- 全部 `IF NOT EXISTS`，只增不删，不碰业务数据。
- 个别语句失败会**打印原因并继续**；想"一错即停"加 `--strict`。
- 若报权限不足 / 用户不存在，改用 `--yes`（会顺带 ensure 用户与库、重授权，幂等）。

**7) 复核**

```bash
python deploy/deploy_db.py --verify      # 期望全部 applied
```

### 场景一注意事项
- 备份没做完不要往下走。
- 第 4 步发现"类型不同/多列"必须先确认，别硬跑。
- 首次纳管老库时所有迁移记为 pending 属正常（老库从没有版本记录），跑一次即补齐。

## 场景二：内网B —— 只装了 PostgreSQL，未初始化任何库

**核心动作：一条命令从零到可用。**

### 步骤

**1) 放入程序 + `.env`**（指向内网B 的 PG）。

> 若管理员不是 `postgres / 123456`，先改 `.env` 的 `POSTGRES_*`；
> 或直接改 `backend/deploy/db_config.py` 里的默认值。

**2) 演练，先看它要做什么**

```bash
python deploy/deploy_db.py --bootstrap --dry-run
```

**3) 一键部署**

```bash
python deploy/deploy_db.py --bootstrap --yes
```

它按顺序做三件事：

1. **建 6 个用户 + 7 个数据库 + 授权**
   （auth、code_review、code_review_regression、static_analysis_filter、
   fpga_static_analysis_filter、opto_knowledge、maintenance）
2. **运行各模块原有 `init_postgresql.py`** → 由各模块 `init_database()`（`create_all`）建立**全部基础表**
3. **应用版本化迁移** → 补列/补表，并写入 `schema_migrations` 版本记录

**4) 复核**

```bash
python deploy/deploy_db.py --verify     # 期望全部 applied
python deploy/deploy_db.py --list       # 查看受管库与迁移清单
```

**5) 检查 bootstrap 阶段有没有 `[!!]` 警告**

若某模块的 init 脚本非 0 退出（会打印 `[!!] [key] 脚本返回码 ...`），说明该库基础表可能没建全。
处理：进该模块目录手工重跑 `python init_postgresql.py --yes`，成功后回 `backend/` 再跑一次：

```bash
python deploy/deploy_db.py --migrate-only --yes
```

> **特别注意 `opto_knowledge`**：它没有任何迁移文件，表结构**完全依赖**它的 init 脚本。
> 若 bootstrap 里它失败，务必单独补跑，否则该模块启动即报缺表。

**6) 启动后端，验证功能。**

### 场景二注意事项
- 空库**不能**只跑 `--yes`（不加 `--bootstrap`）：那只会建库、不会建 ORM 基础表，迁移里的 `ALTER TABLE` 会因为表不存在而失败。
- 无需从本地恢复数据；迁移只执行 SQL，不与本机 pg_dump 版本耦合。
- `--bootstrap` 全流程幂等，跑一半失败可以直接重跑。

## 两场景速查对照

| | **内网A（已有库）** | **内网B（空库）** |
|---|---|---|
| 前置动作 | 先全量备份 | 无 |
| 主命令 | `--migrate-only --yes` | `--bootstrap --yes` |
| 建库/建用户 | 已存在，不动 | 自动创建 |
| 基础表 | 已存在 | 由 init 脚本 / `create_all` 建立 |
| 关键额外动作 | **对账**（information_schema / 快照 diff） | **检查 bootstrap 警告**，补跑失败模块 |
| 幂等可重跑 | 是 | 是 |
| 复核命令 | `--verify` | `--verify` + `--list` |

**三条铁律（两边通用）：先备份 → 先 `--dry-run` → 后 `--verify`。**

---

## 以后改表结构怎么走（两边一致）

1. 在开发机 `backend/deploy/migrations/<库>/` 新建 `V003__描述.sql`，写成幂等语句：
   ```sql
   ALTER TABLE code_review_tasks ADD COLUMN IF NOT EXISTS new_field VARCHAR(50);
   CREATE INDEX IF NOT EXISTS idx_xxx ON code_review_tasks(new_field);
   ```
2. 本机 `python deploy/deploy_db.py --migrate-only --yes` 生效；
3. `--verify` 确认 `applied`；
4. 迁移文件随程序入库；
5. 内网A `--migrate-only --yes`、内网B `--bootstrap --yes` 即自动对齐。

> 版本号只增不改：已应用的迁移文件不要再改内容，需要修正就新增一个 `Vxxx`。
