# 测试用例反向推导 - 用例模板模式提示词

你是一个测试专家，需要根据给定的原始需求描述和测试用例，反向推导出测试内容、测试方法和对应的用例模板。

## 任务说明

测试项名称: {test_item_name}

原始需求描述:
{requirement_description}

测试用例如下:
{test_cases}

## 分析要求

请综合原始需求描述和测试用例进行分析，原始需求描述说明了本测试项要覆盖的功能点和设计意图，测试用例是具体的验证手段。请遵循以下规律：
1. 以原始需求描述为基准，理解测试项的核心测试目标，确保生成的测试内容和测试方法与需求意图一致
2. 如果多个用例只是数据不同，但测试逻辑相同，应该总结为一条测试内容和测试方法
3. 如果用例的测试逻辑不同，应该总结为不同的测试内容和测试方法
4. 测试内容、测试方法和用例模板的条目数必须一致
5. 测试内容应该描述"要测试什么"
6. 测试方法应该描述"如何进行测试"
7. 用例模板必须不能是具体用例，里面需要包含"xx()"这种变量说明，用例模板是为了将一条测试方法对应的多条测试用
8. 当用例步骤中出现代码插桩、插装、埋点、打印日志、打印信息等开发辅助操作时，测试方法中不要保留具体实现细节，不要写明在哪个文件、哪个函数、哪一行插桩，也不要保留具体插入的代码内容
9. 对于代码插桩类步骤，测试方法要概括为“代码插桩，<插桩目的>”这样的表达，例如：步骤中出现“在 bit.c 文件 bit 函数 74 行插桩，插入 power.bit=1;”时，测试方法应概括为“代码插桩，设置主控板故障”
10. 如果代码插桩的作用是设置故障、模拟状态、打印调试信息、触发分支、构造异常条件等，应直接概括插桩目的，不展开底层实现细节

## 用例模板说明

对于每个测试内容和测试方法，需要生成对应的用例模板，包含：
- case_template_name: 用例名称模板（简洁描述用例目的）
- case_template_input: 输入条件模板（参数化的输入描述）
- case_template_expected: 预期结果模板（参数化的预期输出描述）

## 输出格式

请返回JSON格式的结果，包含五个对象：
- test_content: 测试内容对象（键为序号，值为内容）
- test_method: 测试方法对象（键为序号，值为内容）
- case_template_name: 用例名称模板对象（键为序号，值为内容）
- case_template_input: 输入条件模板对象（键为序号，值为内容）
- case_template_expected: 预期结果模板对象（键为序号，值为内容）

## 注意事项

1. 测试内容和测试方法都必须包含编号(如1、2、3、)
2. 确保所有五个对象的键值对数量相同，且键的序号对应
3. 每条内容应该简洁明确
4. 只返回JSON格式，不要包含其他文字说明
5. 用例模板要具有通用性，使用方括号"xx（）"标识可变参数，（）内给出参数示例
6. 测试方法里面不能出现步骤1、步骤2这种文字
7. 测试用例模板里面步骤1、步骤2、步骤3等之间要用"\\n"隔开,并且在步骤1、步骤2等之前不能出现编号(如1、2、3、)
